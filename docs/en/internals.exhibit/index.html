The exhibit, inside

An exhibit is an app that shows another app's recordings: one [raree](../elements.md#raree) per step of each, then the plays on stages. It is served from one directory, the exhibit root, which holds the recordings and the manifest that names them, and it fetches both over http from its own origin (nokre-serve lists no directory, so the manifest is what it reads first). How a recording is made and what it holds is stage.md.

The root

<root>/
  exhibit.json
  scenarios/<scenario>/<tag>.nokreplay
  plays/<play>/<tag>.nokreplay

  • scenarios/ is written by testing.RecordingSink on a driver run's trace — a seeded walk, a journey, a store flow (testing.md). Each run is its own process and writes its own file.

  • plays/ is Plays.recordings from addPlays, installed under the root as it is: the plays runner already writes <play>/<tag>.nokreplay.

  • exhibit.json is written by nokre-exhibit-index (src/exhibit/index_main.zig) over the two.

Nothing else is indexed. A file that is not a .nokreplay is passed over without a word; a .nokreplay at any other place — at the root, directly under scenarios/, a directory deeper, under a third directory — is listed as refused by its path (RecordingIsOutsideTheExhibitLayout), since a recording nobody can reach is a mistake somebody made.

The manifest

exhibit.json is exhibit.ExhibitIndex (src/exhibit/index.zig) written by std.json, and read back by the same type's parse: the writer and the reader are one declaration.

{"revision":202,"app":"Demo","recordings":[{"kind":"scenario","name":"settings_walk","locale":"en","viewport":{"w":440,"h":956},"family":"iphone_6_9","steps":4,"file":"scenarios/settings_walk/en.nokreplay"}],"refused":[{"file":"plays/ballot/fa.nokreplay","error":"RecordedPlayStampDiffers"}]}

Field

Source

revision

the stamp revision of the nokre that wrote the index (recorded_play.stamp); parse refuses any other (error.ExhibitManifestRevisionDiffers), since a recording it names would be refused too

app

the exhibited app's name, the tool's --app

kind

the directory under the root: scenario or play

name

the scenario's or play's directory name

locale

the recording's own locale, read by recorded_play.read

viewport

the window the run was acted at, read the same way

family

the shots.all family whose logical size is exactly the viewport, else null (ExhibitIndex.familyOf)

steps

the recording's step count: what a raree counts and a stage counts as one

file

the path under the root, /-separated on every host, which is the URL the exhibit fetches

refused

each .nokreplay that read refused, or that stands outside the layout, by path and the error's name

Recordings are sorted scenarios first, then by name, then by locale; refusals by path. The bytes are a function of the root.

No sidecar and no merge. Every recording already names its own locale and viewport, and the step count is the recording's. A file written beside each recording would be a second statement of facts the recording holds, and a merge of per-run fragments would be a second writer of one file. The index is read off the recordings, whole, every time.

Read the way the exhibit reads. A recording is admitted by the same read a raree calls, so a file the index lists is one the exhibit can show and a refusal is the one it would meet. That includes the mark rule: a recording whose scenes draw an app's mark is read only by a nokre whose face holds that mark (stage.md, "What a recording holds"). The tool must therefore be built over the nokre the exhibit is built over; nokre's own zig build exhibit-index is built over a face holding no marks, and refuses such a recording by RecordedPlayDrawsAnotherAppsMark.

The tool

zig build exhibit-index -- --app <name> <root>

On success it prints ✓ exhibit.json: N recordings, 0 refused and exits 0. Each refused file is one ✗ <file>: <error> line, the manifest is written anyway so the exhibit shows what it can, the summary is printed under ✗, and the exit is 1. A root holding no .nokreplay at all writes nothing and exits 1 with ✗ no recordings under <root> (error.ExhibitRootHoldsNoRecording).

It is not run per driver run. Driver runs are separate processes, often run side by side; each one rewriting a shared index would race, and the last writer would drop the others' recordings. The index is written once, over the whole root, by whatever serves it.

The build half

addExhibit(b, nokre_dep, .{ .app, .target, .optimize, .plays, .install_dir, .port, .root_url }) builds the exhibit of one app and hands back Exhibit{ app, install, serve }. It takes the consumer's builder for addPlays' reason: what it installs lands in their prefix, at <prefix>/<install_dir>, which is the root.

The root's directory. .install_dir defaults to "exhibit", so an exhibit shares a prefix with the app it shows. "." is the prefix itself: a build that gives each app's exhibit a prefix of its own (--prefix build/exhibit/<app>) would otherwise find its root at build/exhibit/<app>/exhibit, the word doubled and every driver writing into the nested path. The install, the plays, the index and the serve all read the one value. It is relative and stays under the prefix; addExhibit refuses an empty path (error.InstallDirEmpty, since "." is the one spelling of the prefix), an absolute one (error.InstallDirAbsolute) and one with a .. component (error.InstallDirLeavesPrefix), by name, when the build is configured (index_names.checkInstallDir).

A declaration, never sources. The exhibit is nokre's own app, src/exhibit/main.zig, built by addAppTo from a declaration derived from the exhibited app's. Nothing of the exhibited app is compiled or imported: its recordings are data, as a stage's are. Each field of the derived declaration is what it is for one reason:

The app is not required to declare .pkg for anything else, but addExhibit refuses one that does not, by name, since the exhibit's identity is derived from it.

Scene marks. A recording whose scenes draw an app_mark is read only by a nokre whose mark face holds that mark under that app's display name (stage.md, "What a recording holds"). The exhibit's face is given the app's own mark, as markOffer offers it, and the offered_mark of each app in its .links_into, through DeclaredOpts.scene_marks: each is a glyph in the face and a member of MarkedApp (scene_0, scene_1, …), named nowhere in the exhibit's source and so drawn only inside scenes. The module's face and the site's fonts/marks.ttf are written from one list (declaredMarks); a site written from the exhibit's own mark alone ships no mark face, and the page draws the app's mark as a missing glyph. A LinkedApp per mark was the alternative and was not taken: it needs a web_origin and a link the exhibit never writes. The derivation reaches appDeclared and appIcons through exhibit_derivations, keyed by the derived name, because no AppOptions field may carry it without becoming every consumer's.

The install. Exhibit.install puts the site (web) or the executable (native) and the plays:

  • the site into <prefix>/<install_dir> as an overlay — not addInstallExactDirectory, which would prune the scenarios/ the drivers wrote there;

  • .plays, Plays.recordings from addPlays, exactly into <prefix>/<install_dir>/plays, so a play the app stopped declaring is gone.

The drivers write scenarios/ themselves, each run its own process, with RecordingSink.write(io, .cwd(), "zig-out/exhibit") under the default.

The serve step. Exhibit.serve depends on the install, runs nokre-exhibit-index --app <pkg.name> over the root, then serves it with nokre-serve on .port in the fragment form. The index tool is built over the exhibit's own tool_nokre, so it reads every recording with the exhibit's mark face (Read the way the exhibit reads, above). The step does not fail on a refused recording, only on a root with none: the manifest is written either way and the exhibit lists each refusal by file and error at the foot of its page.

The root URL. .root_url is baked into the build. Null means the page's own origin on the web — every fetch is relative, exhibit.json and then each file the manifest names — and http://127.0.0.1:<port>/ on a native target, which has no origin. A native exhibit is built the same way and fetches from the serve step. Since the web fetches only its own origin, the page's connect-src 'self' admits it and no CSP is widened (dom-substrate.md). Each request takes a max_body of 64 MiB, nokre-serve's own max_file_bytes.

What it shows. A top bar of three selects: the language (the locales the manifest's recordings carry — named as text, "Language: en", when the root holds one language, since a select needs two options — opening on the exhibited app's template language — its template catalog's @@locale, read when addExhibit is configured and handed to the page as exhibit_options.template_locale — where the root holds a recording in it, else on the first recording's), the look (eink, depth, lamp, through setTheme) and the device (each family by its logical size, and "As recorded"). Then, per scenario recorded in the chosen language, its name and one raree per step at the device's viewport, null for "As recorded", in one row that wraps them as many to a line as their cells allow (layout.metrics.raree_cell_w: three to a page at its cap, one to a phone's); then each play on a stage on .data; then the refusals. A failed fetch is written in words where its recording would stand, never a panic.

The icon risk, stated rather than closed. A stage's icons are checked at the host's build (render/stage_glyphs.zig) because its plays are declared. An exhibit's recordings are fetched, so no build sees them, and there is no refusal at run time: a recording that draws an icon the exhibit's face lacks draws a hole where the icon would be. The face is the app's own scan, so a recording of that app draws what its sources spell; an icon reached only some other way is the gap.
