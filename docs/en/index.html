nokre

A deliberately limited GUI library: text, lines, and boxes.

Zig and Skia, rasterized on the CPU. Grayscale only. Every element is semantic, so accessibility is derived from the tree you build rather than annotated onto it. Two devices on the same platform with the same logical screen size render byte-for-byte identical frames, run after run. Identity across platforms is not the goal: an app is a semantic tree, and how a device draws that tree is the device's business.

Think: apps for a grayscale Kindle — and, on the same tree, for a terminal, a watch face, a panel that refreshes one row at a time.

const nok = @import("nokre");

fn buildHome(state: *Notes, app: *nok.App) !void {
    const b = app.root();
    try b.text("Everything here is accessible by construction.");
    try b.button(.{
        .label = "New note",
        .on_press = .bind(Notes.newNote, state),
    });
}

That is a complete, keyboard-navigable, screen-reader-complete screen. A button without a label would not have survived append.

The limitation is the product

Every capability a UI toolkit offers is also a way to ship a broken app — inaccessible, inconsistent across machines, untestable without a screenshot farm. nokre keeps only what it can guarantee correct, and turns each removed capability into a promise that holds for every app built on it.

Accessible by construction

Every element is semantic — a heading is structure, a button is a button, a label is mandatory. The accessibility tree and the pixels are both projections of the same semantic tree, so accessibility cannot be added and cannot be omitted. What construction cannot verify, an automatic audit catches.

Deterministic to the pixel

Same logical viewport, same bytes — across runs and machines, on the platform that drew them. Layout is integer math; rendering has no GPU, no hinting, no subpixel tricks. Screenshots are therefore tests: byte-exact, no tolerance, no perceptual diffing.

Testable end to end, headless

nokre ships its own e2e framework, driving the real app through the real event pipeline — no browser driver, no window, no flakiness. Interactions go through the user's pipeline; assertions read the screen reader's snapshot.

What nokre refuses to do

Most of these are load-bearing for a promise above: remove one and it collapses. The rest take away a question the framework never needed answered.

  • No hover states. Interaction is press and release, key, focus, and one gesture. Nothing changes because a pointer floated over it: an affordance only pointer users can discover is information withheld from touch and keyboard users.

  • No transitions or animation. State changes are instant. Motion is a vestibular hazard, an untestable intermediate state, and a tax on determinism. A spinner is animation too — waiting is written in words.

  • No color. Thirteen fixed grays, five semantic aliases, two independent ramps. The whole palette is proven against WCAG contrast in unit tests — floor and ceiling, because past a point more contrast stops buying legibility and starts costing comfort. One honest asterisk, framework-drawn: the Google sign-in button's multicolour G, a trademark whose owner refuses a gray variant. Nothing an app can reach paints in color.

  • No system fonts. Four bundled families, eleven real drawn faces, no synthesis. The moment the OS font stack participates, byte-identity across machines is gone.

  • No GPU. CPU rasterization only. No driver variance, no flicker, no capability matrix — the same bytes everywhere is only promisable when no driver is involved.

  • No fractional scaling. Layout is integer logical pixels; hidpi is an integer scale factor, so a 2× frame is exactly the 1× frame at double density.

  • No custom widgets, no styling system. The element set is closed. A styling hook is an accessibility loophole: contrast, target size and labeling can only be enforced on elements the framework owns.

  • No paths. A reference names a screen — note~42 — and says nothing about where the screen sits, because screens do not sit anywhere.

They are guarantees, not gaps: an app built on nokre cannot have these problems, because the library cannot express them. The argument, in full, is the introduction.

The refusals buy something quieter as well: a nokre app at rest costs zero CPU. No ticker, no vsync loop, no animation frames — a frame renders when state changes, and otherwise nothing runs.

Six platforms, full parity

All five shells are working: window, input, IME, clipboard, and a screen reader on each. What differs at a glance is the text scaler and the accessibility backend.

This site is a nokre app

Every page here — this one included — is a nokre element tree. The generator builds each screen through tree.append, runs nokre's accessibility audit over it, and then writes the tree out as HTML instead of pixels. The stylesheet's grays, type scale and metrics are read out of nokre's own source at build time. What that means, and where the edition stops short, is the colophon.
